# 回款计划录入 / 实际回款期数核销 / 收入确认模块 实施计划

## 一、Summary（目标概述）

在现有 CRM（合同回款管理系统）上新增/增强四块能力：

1. **回款计划**：支持单行录入与批量导入，硬校验「同一合同回款计划合计必须恰好等于合同金额」。
2. **实际回款**：新增「期数」字段，登记时按「合同 + 期数」自动定位回款计划并核销（期数必填，允许部分核销）。
3. **收入确认管理**：新增独立模块，收入明细**与回款计划同时录入**（同一事务），支持批量导入收入明细，字段预设。
4. **收入联动校验（新增）**：
   - 时点平衡公式：在任一收入确认时点 T，`该合同截至 T 的含税收入合计 = T 之前该合同实际回款合计 + T 之后该合同计划回款（待核销）合计`；
   - 合同级硬校验：`同一合同收入合计 = 合同金额`（严格等号）。

不改动既有客户、合同主流程；所有改动遵循项目现有 Controller → Service → Mapper、EasyExcel 导入、`ImportResultVO` 回执、`SaCheckPermission` 权限点、Flyway 迁移、Vue3 + Element Plus 页面模式。

## 三、Assumptions & Decisions（关键决策）

### 已由用户确认

| 编号 | 决策 |
|---|---|
| D1 | **回款计划合计硬校验**：新增 / 编辑 / 批量录入 / 导入后，「该合同未删除计划金额合计」必须**恰好等于** `contract.amount`。 |
| D2 | **实际回款期数必填**，按「合同 + 期数」定位唯一计划核销，**允许部分核销**（差额留在 `payment_record.unallocated_amount`，不跨期）。 |
| D3 | **收入明细与回款计划同时录入**（同一事务一次提交）。 |
| D4 | **时点平衡校验**：对每条收入记录以其确认日期 T 校验 `含税收入累计(≤T) = 实际回款累计(≤T) + 计划待核销(>T)`。 |
| D5 | **收入合计硬校验**：`同一合同收入明细合计 = 合同金额`（严格等号）。 |

### 由现状推导、需要落实的决策

| 编号 | 决策 | 理由 |
|---|---|---|
| D6 | 删除回款计划 / 删除收入明细时**不做**合计校验（允许暂时产生差额），页面用红色「差额」标签提示 | 硬校验若覆盖删除则无法删除任何记录；录入类操作仍严格拦截 |
| D7 | 提供「**整批录入**」入口（同一合同的收入明细多行 + 回款计划多行，一次提交，事务内校验后落库） | 硬等号下逐条录入几乎不可用（除非恰好补足差额），必须提供整批提交能力 |
| D8 | 回款计划 / 收入明细 Excel 导入均按「**合同整组原子处理**」：组内合计等于合同金额（及收入组内时点平衡）才写入，否则整组失败并把错误回写到该组每一行 | 硬校验是合同级约束，无法逐行独立通过；避免半套数据入库 |
| D9 | 回款计划导入为**覆盖模式**（软删该合同原有计划后写入）；该合同已有计划 `settled_amount > 0` 时整组拒绝 | 避免销毁已核销数据 |
| D10 | `payment_record.period_no` 在 DB 层允许 `NULL`（兼容历史数据），业务层（DTO `@NotNull`、导入必填）强制非空 | 纯 `ADD COLUMN NOT NULL` 对存量数据不友好；业务校验即可 |
| D11 | `CreateRecordDTO` 移除 `targetPlanIds`，改为 `periodNo`；`ManualSettleDTO.planIds` 保持（手工核销为独立能力） | 期数必填后登记回款不再需要手选期次 |
| D12 | **公式口径**：`T` = 收入记录的 `recognize_date`；<br>`INCOME(≤T)` = `SUM(revenue_record.amount) WHERE contract_id=X AND recognize_date ≤ T AND is_deleted=0`（保存时含本次待写入记录）；<br>`RECEIVED(≤T)` = `SUM(payment_record.amount) WHERE contract_id=X AND arrival_date ≤ T AND status='NORMAL' AND is_deleted=0`（`REVERSED` 原单与负数 `RED` 单均排除，净额正确）；<br>`PLAN_UNSETTLED(>T)` = `SUM(payment_plan.unsettled_amount) WHERE contract_id=X AND plan_date > T AND is_deleted=0`（已核销部分已计入实际回款，不重复计算） | 口径唯一化，避免重复计入 |
| D13 | **校验时机**：单条 / 整批 / 导入保存时全部硬校验；整批提交时按 `recognize_date` 升序**逐条**校验时点平衡，再校验合同级收入合计 | 保证每条记录的时点都成立，而非仅末态成立 |
| D14 | 收入导入只承载收入明细（不含计划行），因此导入前置条件：该合同的回款计划必须已录入且合计等于合同金额，否则该组报错「请先录入回款计划」 | 保持「收入与计划同录」的业务语义，避免无计划状态下确认收入 |
| D15 | 收入明细预设字段（用户授权自行预设）见下表；金额采用「含税金额 + 税率」推导「税额 / 不含税金额 / 毛利」 | 兼顾财务口径与录入成本 |

```java
/** 硬校验：该合同未删除计划合计（含本次新增金额）必须恰好等于合同金额。 */
private void assertTotalEqualsContract(Long contractId, Long excludePlanId, BigDecimal incoming) {
    Contract c = contractMapper.selectById(contractId);
    if (c == null) throw new BizException(ErrorCode.CT_NOT_FOUND);
    BigDecimal total = planMapper.sumPlanAmountExcluding(contractId, excludePlanId).add(incoming);
    if (total.compareTo(c.getAmount()) != 0) {
        throw new BizException(ErrorCode.PM_PLAN_AMOUNT_MISMATCH,
            "回款计划合计 " + total + " 与合同金额 " + c.getAmount()
            + " 不一致，差额 " + c.getAmount().subtract(total));
    }
}
```

### 4.3 后端 · 回款计划批量导入

**新增** `payment/service/PaymentPlanImportService.java` + `impl/PaymentPlanImportServiceImpl.java`

- `HEADERS = {"合同编号","期数","计划日期","计划金额","提醒天数","备注"}`
- 流程（两阶段，区别于现有逐行导入）：
  1. 复用 `ExcelImportHelper`（`validateHeader` / `isEmptyRow` / `MAX_ROWS` / `parseDateFlexible` / `parseAmount` / `checkLength` / `trim`）解析所有数据行，保留 `rowIndex`；
  2. 按 `合同编号` 分组；
  3. 逐组：合同存在 → 组内期数不重复 → 组内合计 `compareTo(contract.amount) != 0` 报差额 → 现有计划有核销记录则拒绝 → `paymentPlanService.batchSave(...)`；
  4. 组失败：该组所有行写入 `RowError(rowIndex, msg)` 并累加 `failed`；组成功按行累加 `success`；`total` = 有效行数；
  5. 读取层异常处理与现有 `PaymentImportServiceImpl.unwrapMessage` 保持一致。
- 依赖 `ContractMapper` + `PaymentPlanService`，不直接操作 `payment_plan`，保证合计校验只有一处实现。

### 4.4 后端 · 实际回款期数与按期限核销

- **`PaymentRecord`**：新增 `private Integer periodNo;`
- **`CreateRecordDTO`**：移除 `targetPlanIds`，新增 `@NotNull @Positive private Integer periodNo;`
- **`SettlementService` / `SettlementServiceImpl`** 新增：

```java
/** 按「合同 + 期数」定位计划核销；金额不足则部分核销，剩余留在 record.unallocated_amount。 */
BigDecimal settleByPeriod(PaymentRecord record, Integer periodNo);
```

实现（沿用现有事务与行锁约定）：
1. `recordMapper.selectForUpdate(record.getId())`；已 `REVERSED`/`RED` → 原异常；
2. `planMapper.selectByContractAndPeriodForUpdate(contractId, periodNo)` 为 `null` → `BizException(PM_PLAN_NOT_FOUND, "第 X 期回款计划不存在")`；
3. `SETTLED` → `BizException(PM_PLAN_SETTLED, "第 X 期已结清")`；
4. `portion = min(remaining, plan.unsettledAmount)`；`portion <= 0` 只回写 `unallocated_amount`；
5. 写 `payment_settlement`（`settle_type='AUTO'`）、更新 plan（`PARTIAL`/`SETTLED`）、乐观锁失败抛 `SYS_ERROR`；
6. 回写 `payment_record.unallocated_amount = remaining - portion`。

- **`PaymentRecordServiceImpl.create`**：写入 `periodNo`，改调 `settleByPeriod(r, dto.getPeriodNo())`；`manualSettle` 保持原 `settle(record, planIds)`。
- **`RecordQuery`** 增加 `Integer periodNo`；**`page`** 增加 `w.eq("period_no", ...)` 条件；**`PaymentRecordVO`** 增加 `periodNo`。
- **`PaymentImportServiceImpl`**：`HEADERS = {"合同编号","期数","到账日期","金额","付款方","凭证号","备注"}`；`importRow` 增加期数解析（正整数），校验顺序沿用：合同存在 → 期数 → 到账日期 → 金额 → 字段长度 → 文件内凭证号去重。

**`RevenueBalanceValidator`（D4 + D5 + D13）**

```java
/** 校验链：字段 → 计划合计=合同金额 → 逐条时点平衡 → 收入合计=合同金额。 */
void validateContract(Long contractId, List<RevenueRecord> incoming, Long excludeRevenueId,
                      BigDecimal newPlanSum);
```

1. **计划合计**：若 `newPlanSum != null`，`planSumExcluding + newPlanSum` 必须等于 `contract.amount`（复用 `assertTotalEqualsContract` 的语义，通过 `PaymentPlanService` 暴露一个只读校验方法，避免重复实现）。
2. **逐条时点平衡**（D12 口径，按 `recognizeDate` 升序）：
   ```java
   for (RevenueRecord r : incomingSortedByDate) {
       LocalDate t = r.getRecognizeDate();
       BigDecimal lhs = revenueMapper.sumAmountUpTo(contractId, t, excludeRevenueId).add(r.getAmount());
       BigDecimal received = paymentRecordMapper.sumEffectiveAmountUpTo(contractId, t);
       BigDecimal futurePlan = planMapper.sumUnsettledAfter(contractId, t);
       if (lhs.compareTo(received.add(futurePlan)) != 0) {
           throw new BizException(ErrorCode.RV_BALANCE_MISMATCH,
               "确认日期 " + t + " 处不满足时点平衡：含税收入累计 " + lhs
               + " ≠ 已回款 " + received + " + 后续计划待收 " + futurePlan
               + "（差额 " + lhs.subtract(received.add(futurePlan)) + "）");
       }
   }
   ```
   > 说明：`sumAmountUpTo` 需排除本次批量中尚未落库、但 `recognize_date > t` 的记录天然不影响结果；对已落库记录用 `excludeRevenueId` 排除编辑中的记录。
3. **合同级合计**：`revenueMapper.sumAmountByContract(contractId, excludeRevenueId).add(Σincoming.amount)` 必须 `compareTo(contract.amount) == 0`，否则 `RV_AMOUNT_MISMATCH("同一合同收入合计 X 与合同金额 Y 不一致，差额 Z")`。

**`RevenueBundleServiceImpl.saveBundle`**
1. 合同存在校验；
2. 若 `plans` 非空 → 先 `paymentPlanService.saveForContract(contractId, plans, planOverwrite)`（内部完成计划合计硬校验）；
3. 构造 `RevenueRecord` 列表并 `applyDerived`；
4. `validator.validateContract(contractId, records, null, plans==null ? null : Σplans.planAmount)`；
5. 逐条 `mapper.insert`；
6. 返回 `RevenueSummaryVO`。
